## Свой репозиторий на GitHub

Нужны Git, учётная запись GitHub и выполненная первая работа. В этом репозитории вы будете вести
и следующие лабораторные, поэтому создайте его один раз.

1. На GitHub нажмите **+ → New repository** (правый верхний угол).
2. **Repository name** — `cs-practice`. Видимость — **Public**: сервис проверки читает только
   публичные репозитории.
3. Галочки **Add a README**, **.gitignore** и **license** **не ставьте** — репозиторий должен быть пустым.
   Нажмите **Create repository**.
4. На странице нового репозитория выберите **HTTPS** и скопируйте адрес вида
   `https://github.com/ваш-логин/cs-practice.git`.

Клонируйте репозиторий, подставив свой адрес вместо `YOUR_REPO_URL`:

```bash
git clone YOUR_REPO_URL cs-practice
cd cs-practice
git status
git remote -v
```

Предупреждение `You appear to have cloned an empty repository` — это нормально: коммитов пока нет.
`origin` должен указывать на **ваш** репозиторий `cs-practice`.

> ⚠️ **`git init` выполнять не нужно** — `clone` уже создал репозиторий и связал его с GitHub.
> Лишний `init` внутри него заведёт отдельную историю, и ваши коммиты не попадут на GitHub.

Все дальнейшие команды выполняются **из корня репозитория**. Создайте в корне папку `lab02` — в ней
будете вести `NOTES.md`.

## Автор коммитов

```bash
git config user.name "Ваше имя"
git config user.email "ВАШ_EMAIL"
```

Команды задают автора коммитов в текущем репозитории — они **не выполняют вход** в GitHub.
Для `push` используйте настроенный способ авторизации GitHub.

## Акцент для ФИИТ

В `NOTES.md` опишите роли редактора, терминала, Git и GitHub и порядок сохранения и публикации изменения.

## Часть 1. Три коммита в `main`

### 1. Первый коммит: локальные состояния

Создайте `lab02/NOTES.md`. Своими словами определите **рабочую папку**, **индекс** и **коммит**.
Добавьте пояснение для своего направления. Сохраните файл, затем:

```bash
git status
git add lab02/NOTES.md
git diff --staged
git commit -m "Describe local Git states"
git branch -M main
git log --oneline
```

`git branch -M main` называет основную ветку `main`, даже если Git по умолчанию назвал её `master`.
Проверьте: `git branch --show-current` должен вывести `main`.

### 2. Второй коммит: Git и GitHub

Дополните `NOTES.md` различием Git и GitHub. **До `add`** посмотрите изменения рабочей копии,
**после `add`** — подготовленные изменения. Запишите, почему после `add` файл ещё не опубликован на GitHub.

```bash
git diff
git add lab02/NOTES.md
git diff --staged
git commit -m "Explain Git and GitHub"
```

### 3. Третий коммит: команды и первая отправка

Допишите в `NOTES.md` раздел «Использованные команды»: что делают `git status`, `git add`,
`git diff`, `git diff --staged` и `git commit`. Сохраните отдельным коммитом и отправьте на GitHub:

```bash
git add lab02/NOTES.md
git commit -m "List Git commands used"
git push -u origin main
```

Ключ `-u` связывает локальную `main` с `main` на GitHub — дальше хватит короткого `git push`.
Откройте свой репозиторий в браузере и проверьте, что `lab02/NOTES.md` и три коммита появились на GitHub.

## Часть 2. Работа с веткой

Ветка — отдельная линия истории. В ней можно спокойно вносить изменения, не трогая `main`,
а когда работа готова — влить её обратно.

### 4. Четвёртый коммит — в отдельной ветке

Создайте ветку и сразу перейдите в неё:

```bash
git switch -c explain-branches
git branch
```

`git branch` покажет две ветки; звёздочка стоит у текущей. Допишите в `NOTES.md` раздел **«Ветки»**:
что такое ветка, что происходит с ней при новом коммите и что делает слияние. Сохраните и закоммитьте:

```bash
git add lab02/NOTES.md
git commit -m "Explain branches"
git log --oneline --graph --all
```

### 5. Вернитесь в `main` и посмотрите разницу

```bash
git switch main
```

Откройте `NOTES.md` в редакторе — **раздела «Ветки» здесь нет**: он закоммичен только в ветке
`explain-branches`. Запишите для себя, почему так происходит, — это вопрос защиты.

### 6. Слейте ветку в `main`

```bash
git merge --no-ff explain-branches -m "Merge branch explain-branches"
git log --oneline --graph
```

Раздел «Ветки» появился и в `main`. В графе видно, как ветка отошла от `main` и вернулась в неё
**коммитом слияния**.

> Зачем `--no-ff`: пока вы работали в ветке, `main` не менялась. Без этого ключа Git просто
> передвинул бы `main` вперёд (*fast-forward*) — коммита слияния не появилось бы, и в истории
> не осталось бы следа ветки. Сервис ищет именно коммит слияния.

Ветка больше не нужна — удалите её и отправьте результат:

```bash
git branch -d explain-branches
git push
```

Удаляется только имя ветки: её коммит уже входит в историю `main`.

Каждый коммит должен содержать реальное изменение. Пустые коммиты не заменяют шаги работы.

## Как сдать

```bash
git rev-parse HEAD
```

В сервисе проверки → **Отправить решение** → «Лабораторная 02». Укажите ссылку на свой репозиторий
(`https://github.com/ваш-логин/cs-practice`), а в поле ветки — `main` или полный SHA из команды выше:
сервис проверит ровно этот коммит.

Затем **продублируйте сдачу в [Moodle](../../README.md#moodle)**: ссылку на свой репозиторий и тот же полный SHA.

## Что проверяется автоматически

Сервис читает всю историю вашего репозитория.

| Что смотрит сервис | Что от вас нужно |
|---|---|
| собственные коммиты | не меньше четырёх, каждый — реальное изменение |
| `NOTES.md` | раскрыты рабочая папка, индекс, коммит, различие Git и GitHub и ветки |
| сообщения коммитов | по сообщению понятно, что изменилось: не `update`, `fix` или `1` |
| ветвление | в истории есть коммит слияния ветки |
| публикация | коммиты есть в вашем репозитории на GitHub |
