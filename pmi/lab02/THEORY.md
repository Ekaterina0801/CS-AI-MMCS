## Зачем нужен контроль версий

Система контроля версий сохраняет выбранные состояния проекта и сведения об их происхождении.
В процессе работы меняются формулы, входные данные и способ вывода. По одному текущему файлу
нельзя надёжно восстановить, что изменилось и почему. История версий связывает результат
с конкретным состоянием исходного кода.

> **Пример.** Версия 1: числа заданы в коде. Версия 2: числа вводит пользователь.
> Версия 3: добавлена инструкция запуска. Три коммита — три законченных этапа.

Git появился в 2005 году при разработке ядра Linux. Он **распределённый**: история может находиться
в нескольких репозиториях, и локальный коммит не требует подключения к интернету.

## Git и GitHub — разные вещи

| | Что это | Что делает |
|---|---|---|
| **Git** | программа на вашем компьютере | `add`, `commit`, `log` и другие команды истории |
| **GitHub** | сервис в интернете | хранит репозитории, даёт доступ участникам, обсуждение изменений |
| **Учётная запись GitHub** | ваш аккаунт | нужна для работы с GitHub, **не нужна** для локального `commit` |

Локальный репозиторий существует независимо от GitHub. Удалённый репозиторий — просто ещё один
участник обмена версиями.

## Что такое репозиторий

Репозиторий хранит историю проекта. Служебные данные Git лежат в скрытой папке `.git`, рядом —
обычные рабочие файлы, которые вы открываете в редакторе. Папка с `main.py` сама по себе ещё не
репозиторий: историю создаёт Git.

## Три области и четвёртое место

```
 рабочая папка ──git add──▶ индекс ──git commit──▶ история ──git push──▶ GitHub
   (файлы на диске)        (что войдёт           (коммиты,            (удалённый
                            в коммит)             локально)            репозиторий)
```

| Область | Что в ней | Что её меняет |
|---|---|---|
| **Рабочая папка** | текущие файлы на диске | сохранение в редакторе |
| **Индекс** (staging area) | подготовленный снимок для следующего коммита | `git add` |
| **История** | зафиксированные снимки проекта | `git commit` — создаётся **из индекса** |
| **GitHub** | удалённая копия истории | `git push` |

Сохранение в редакторе меняет только рабочий файл. `add` выбирает содержимое. `commit` создаёт
версию. GitHub получает коммиты **только после успешного `push`**.

## Состояния файлов

Одна и та же правка проходит несколько состояний, и `git status` показывает, где она сейчас.

| Состояние в `git status` | Что значит |
|---|---|
| **Untracked** | новый файл ещё не отслеживается |
| **Changes not staged for commit** | файл изменён, но правка не подготовлена |
| **Changes to be committed** | подготовленные изменения попадут в следующий `commit` |
| **nothing to commit, working tree clean** | несохранённых в истории изменений нет |

Короткая форма `git status --short` показывает две колонки: **первая — индекс**, **вторая — рабочая папка**.

| Вывод | Смысл |
|---|---|
| `?? main.py` | файл не отслеживается |
| `A  main.py` | новый файл добавлен в индекс |
| ` M main.py` | изменён, но не подготовлен |
| `M  main.py` | изменение подготовлено к коммиту |
| `MM main.py` | подготовлена одна версия, а после `add` файл изменили ещё раз |

## Индекс — снимок на момент `add`

Это самое неочевидное место. `git add` копирует в индекс **содержимое файла в момент команды**,
а не «запоминает файл».

> **Пример.** В истории `print(10)`. Вы исправили на `print(20)` и выполнили `git add`.
> Потом снова исправили на `print(30)` и сохранили. `git status --short` покажет `MM main.py`.
> Обычный `git commit` сохранит **`print(20)`** — версию из индекса. Чтобы включить `print(30)`,
> повторите `git add` перед коммитом.

## Два разных `diff`

| Команда | Что сравнивает | Когда полезна |
|---|---|---|
| `git diff` | рабочую папку с **индексом** | что изменено, но ещё не подготовлено |
| `git diff --staged` | индекс с **последним коммитом** | что именно уйдёт в следующий коммит |

Строки с `-` — старое содержимое, с `+` — новое. После `git add` обычный `git diff` становится пустым
(файл совпадает с индексом), а `git diff --staged` показывает подготовленную правку.

## Коммит и история

Коммит фиксирует подготовленный снимок проекта вместе с автором, временем и сообщением.
Один коммит должен выражать **одно законченное изменение**, а сообщение — говорить, что изменилось.

```bash
git commit -m "Read values from input"
git log --oneline
```

```
8b2e4c1 Read values from input
4a1d7f0 Add initial calculation
```

Слева — сокращённый идентификатор (SHA), справа — сообщение; новые коммиты выше старых.
Если `log` открылся в просмотрщике, выйдите клавишей `q`. Полный SHA текущей версии —
`git rev-parse HEAD`.

Имя автора (`git config user.name`) и вход в GitHub — **разные настройки**. Имя подписывает
коммиты, но не даёт права отправлять их.

## Ветки

**Ветка** — именованная ссылка на коммит, которая продвигается при новых коммитах. Основная ветка
в курсе — `main`; это соглашение, а не особый тип кода. Текущая ветка: `git branch --show-current`.

Ветки позволяют вести изменение отдельно: пробовать, ошибаться и дописывать, пока `main` остаётся
в рабочем состоянии. Когда изменение готово, ветку **сливают** обратно.

```
                  ● Explain branches          ← explain-branches
                 ╱                 ╲
● ── ● ── ● ────●───────────────────● Merge   ← main
```

| Команда | Что делает |
|---|---|
| `git switch -c имя` | создать ветку от текущего коммита и перейти в неё |
| `git branch` | список веток; `*` — текущая |
| `git switch main` | перейти в `main`: файлы рабочей папки примут её состояние |
| `git merge имя` | влить ветку в текущую |
| `git branch -d имя` | удалить слитую ветку — только имя, коммиты остаются в истории |
| `git log --oneline --graph --all` | нарисовать историю всех веток |

**Переключение меняет файлы.** `git switch` подставляет в рабочую папку состояние коммита, на который
указывает ветка. Правка, закоммиченная в другой ветке, в `main` не видна, пока ветки не слиты.
Перед переключением закоммитьте изменения: `git status` должен быть чистым.

**Fast-forward и `--no-ff`.** Если после создания ветки в `main` новых коммитов не было, `git merge`
просто передвигает `main` вперёд на последний коммит ветки — это *перемотка* (fast-forward).
История получается прямой, и следа ветки в ней нет. Ключ `--no-ff` заставляет создать **коммит
слияния** — коммит с двумя родителями, по которому видно, что работа велась в ветке.

> Если одну и ту же строку изменили в обеих ветках, Git не может выбрать версию сам — это
> **конфликт**. Разрешать конфликты вы будете в следующих работах.

## README и `.gitignore`

`README.md` описывает назначение проекта, запуск и формат данных — чтобы другой человек повторил
запуск без устных подсказок.

`.gitignore` перечисляет файлы, которые **не нужно** отслеживать: окружение и служебные файлы.

```
.venv/
__pycache__/
*.pyc
```

Сам `.gitignore` хранится в истории вместе с проектом.

## Удалённый репозиторий и `push`

`remote` — сохранённое имя адреса другого репозитория. `origin` — распространённое имя, а не
встроенное обозначение GitHub. Посмотреть адреса: `git remote -v`.

`git push origin main` передаёт недостающие коммиты и обновляет ветку `main` на GitHub. Локальные
коммиты при этом остаются у вас. Новый локальный коммит **не появляется** на GitHub автоматически.

При отправке GitHub проверяет, кто вы и есть ли у вас право записи. Пароль от аккаунта не используется
как пароль для Git по HTTPS — применяется вход через браузер или токен. **Токен никогда не записывают
в код** и не коммитят.

## Свой репозиторий: как это устроено в курсе

Работы ведутся в **вашем собственном репозитории** `cs-practice` на GitHub. Вы создаёте его пустым
(**New repository**, без README), клонируете и дальше коммитите и отправляете изменения туда.
Репозиторий курса вы только читаете — условия новых лабораторных открывайте в нём на GitHub.

Есть два способа связать локальную папку с репозиторием на GitHub:

| Способ | Команды | Когда удобен |
|---|---|---|
| **clone** пустого репозитория | `git clone АДРЕС cs-practice` | начинаете с нуля — так в курсе |
| **init** и подключение `origin` | `git init` · `git remote add origin АДРЕС` | папка с кодом уже есть на компьютере |

Если правили файлы на сайте GitHub, на сервере появятся коммиты, которых нет у вас, и `push` будет
отклонён. Тогда сначала `git pull`, затем снова `git push`. Не применяйте `push --force`.
